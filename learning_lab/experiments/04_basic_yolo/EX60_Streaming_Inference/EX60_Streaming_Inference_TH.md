# 🧠 EX60: การทำนายผลแบบสตรีมมิ่ง (Streaming Inference)

เมื่อต้องการประมวลผลไฟล์วิดีโอที่มีความยาวมาก หรือไฟล์สตรีมมิ่งสดผ่านเครือข่ายอย่างต่อเนื่อง (เช่น กล้องวงจรปิดผ่านโปรโตคอล RTSP, RTMP หรือเว็บแคม) การรันการทำนายผลรูปแบบมาตรฐาน (`results = model(source)`) จะทำให้เกิดจุดอ่อนสำคัญคือ **การสะสมข้อมูลล้นหน่วยความจำ (Memory Accumulation)**

ตามปกติแล้ว YOLO จะทำการรวบรวมอ็อบเจกต์ `Results` ที่ทำนายได้จากทุกๆ เฟรมเก็บสะสมไว้ในหน่วยความจำ RAM ของระบบ และส่งคืนค่ากลับมาเป็นรายการลิสต์ (list) ชุดใหญ่ทีเดียวหลังจากสตรีมหรือวิดีโอนั้นสิ้นสุดลง สำหรับการสตรีมกล้องวงจรปิดตลอด 24 ชั่วโมงทุกวัน หรือการประมวลผลวิดีโอขนาดหลายกิกะไบต์ การทำเช่นนี้จะกินแรมระบบเพิ่มขึ้นเรื่อยๆ จนกระทั่งระบบล่มเนื่องจาก **หน่วยความจำเต็ม (Out-Of-Memory หรือ OOM)**

เพื่อแก้ไขปัญหานี้ YOLO จึงจัดเตรียมโหมดการตรวจจับแบบสตรีมมิ่งที่มีประสิทธิภาพสูงและประหยัดการใช้แรม ผ่านพารามิเตอร์ `stream=True` ในเมธอด `model.predict()`

---

## 1. ข้อแตกต่างระหว่างการทำนายผลแบบปกติและแบบสตรีมมิ่ง

| คุณสมบัติ | การทำนายผลปกติ (`stream=False`) | การทำนายผลแบบสตรีมมิ่ง (`stream=True`) |
| :--- | :--- | :--- |
| **ประเภทค่าส่งคืน** | รายการลิสต์ (`list`) ของวัตถุ `Results` | ออบเจกต์เจเนอเรเตอร์ (`generator`) ที่ทยอยส่ง `Results` |
| **ความซับซ้อนของ RAM** | $O(N)$ — ขยายใหญ่ขึ้นตามจำนวนเฟรมทั้งหมด | $O(1)$ — คงที่ตลอดเวลาไม่ว่าวิดีโอจะยาวเท่าใด |
| **ตัวอย่างการใช้งาน** | การทำนายผลภาพกลุ่มย่อยหรือวิดีโอสั้นๆ | สตรีมเว็บแคมสด, กล้องวงจรปิด RTSP, ไฟล์วิดีโอยาวมาก |
| **การจัดการหน่วยความจำ** | เก็บผลตรวจจับกล่องและคลาสของทุกเฟรมค้างไว้ใน RAM | ลบผลลัพธ์ของเฟรมเก่าทิ้งจาก RAM ทันทีในแต่ละรอบลูป |

## 2. ตัวอย่างการเขียนโค้ดด้วย Python (Python Code Demonstration)

ตัวอย่างด้านล่างแสดงวิธีการเขียนลูปประมวลผลวิดีโออย่างปลอดภัยต่อหน่วยความจำ:

```python
from ultralytics import YOLO

# 1. โหลดโมเดลที่ฝึกสอนไว้ล่วงหน้า
model = YOLO("yolo11n.pt")

# 2. กำหนดแหล่งข้อมูลอินพุต (เช่น ไฟล์วิดีโอ หรือพาธสตรีม RTSP)
video_source = "traffic.mp4"

# 3. เรียกใช้งานเมธอด predict พร้อมตั้งค่า stream=True
# คำสั่งนี้จะส่งอ็อบเจกต์เจเนอเรเตอร์กลับมาทันทีโดยยังไม่เริ่มกระบวนการทำนายทั้งหมด
results_generator = model.predict(source=video_source, stream=True)

print("เริ่มการทำนายผลแบบสตรีมมิ่งแล้ว...")
print(f"ชนิดของตัวแปรเจเนอเรเตอร์: {type(results_generator)}")

# 4. ลูปผ่านตัวแปรเจเนอเรเตอร์
# เฟรมวิดีโอจะถูกโหลด ทำนายผล และส่งผลลัพธ์ทีละเฟรมสลับกันไป
for frame_idx, result in enumerate(results_generator):
    # ดึงข้อมูลกล่องขอบเขตวัตถุของเฟรมปัจจุบัน
    boxes = result.boxes
    
    # ประมวลผลผลลัพธ์ตรวจจับ
    num_detections = len(boxes)
    print(f"เฟรมที่ {frame_idx}: ตรวจพบวัตถุ {num_detections} รายการ")
    
    # ใส่ตรรกะทางธุรกิจที่ต้องการตรงนี้
    # ตัวอย่าง: หากตรวจพบประเภทคลาสที่ต้องการด้วยความมั่นใจสูง ให้สั่งทำงานระบบเตือนภัย
    for box in boxes:
        cls_id = int(box.cls[0].item())
        conf = float(box.conf[0].item())
        if model.names[cls_id] == "person" and conf > 0.8:
            print(f"--> [ALERT] พบมนุษย์ในเฟรมที่ {frame_idx}!")
            
    # ความปลอดภัยของหน่วยความจำ (Memory Safety):
    # เมื่อจบรอบการทำงานของลูป ตัวแปรอ้างอิงของ 'result' จะถูกอัปเดตค่าใหม่
    # ระบบจัดการขยะ (Garbage Collector) ของ Python จะทำการล้างหน่วยความจำของเฟรมก่อนหน้าโดยอัตโนมัติ
```

## 💡 คำแนะนำจากอาจารย์ (Professor Tips)

### 1. ข้อจำกัดของโครงสร้างเจเนอเรเตอร์ (The Generator Gotcha)
เนื่องจากเมธอด `model.predict(..., stream=True)` ส่งค่ากลับมาในรูปแบบตัวสร้างข้อมูล (Python Generator) คุณจึง **ไม่สามารถ** เข้าถึงดัชนี (index) หรือเช็คขนาดความยาวของมันได้โดยตรง:
```python
results = model.predict(source="traffic.mp4", stream=True)

# ❌ คำสั่งด้านล่างนี้จะส่งผลให้เกิด Error ของโปรแกรม:
# print(len(results))       # TypeError: object of type 'generator' has no len()
# print(results[0])         # TypeError: 'generator' object is not subscriptable
```
คุณต้องเข้าถึงข้อมูลผ่านการใช้ลูป `for`, ฟังก์ชัน `next()` หรือหากจำเป็นต้องแปลงเป็นลิสต์ก็ใช้ `list(results)` (แต่โปรดทราบว่าการแปลงเป็นลิสต์จะทำให้สูญเสียประสิทธิภาพในการประหยัดแรมและอาจทำให้แรมเต็มได้เช่นเดิม)

### 2. ปัญหาเฟรมหน่วงในระบบสตรีมมิ่งสด (Live Stream Frame Dropping)
ในกรณีสตรีมมิ่งสดผ่านเครือข่ายเรียลไทม์ (เช่น RTSP) หากมีความล่าช้าของเครือข่ายหรือโหลดการประมวลผลของการ์ดจอสูง อาจส่งผลให้โมเดลทำประมวลผลเฟรมได้ช้ากว่าอัตราเฟรมที่ไหลเข้ามาจริง
ตัวอย่างเช่น หากโมเดลใช้เวลาประมวลผล $40 \text{ ms}$ ต่อเฟรม ($25 \text{ FPS}$) แต่ภาพสตรีมสดไหลเข้ามาด้วยอัตรา $30 \text{ FPS}$ จะเกิดการสะสมตัวของบัฟเฟอร์ในระบบ ทำให้ภาพที่แสดงมีความล่าช้าสะสมสูงขึ้นเรื่อยๆ เพื่อป้องกันปัญหานี้:
*   ระบุค่า `vid_stride` (เช่น `vid_stride=2`) เพื่อข้ามการประมวลผลบางเฟรม เพื่อให้ความเร็วในการประมวลผลตามทันเหตุการณ์สดจริง
*   แยกส่วนลูปคำนวณการทำนายผลออกเป็นเธรดเบื้องหลัง (Background Thread) ที่มีหน้าที่ดึงเฉพาะ *เฟรมล่าสุด* ในบัฟเฟอร์มาใช้งานเท่านั้น แล้วทำการลบหรือข้ามเฟรมเก่าๆ ทิ้งไป
